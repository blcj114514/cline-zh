## 二、审计方法（可复现）

1. **识别运行架构**：探测 `cline-app.exe` 内嵌资源表，确认前端资源以 **brotli 压缩**内嵌在 9.4 MB–13.3 MB 区间，格式为 `[路径] + 0x1B 标记 + 3 字节小端长度 + brotli 流`。
2. **还原前端**：用 `brotli.Decompressor` 流式解压，成功还原 **390 / 398** 个 Next.js chunk（约 19 MB）。
3. **还原后端**：Bun 编译产物中保留了**完整可读、带缩进的 JavaScript 源码**，提取出 **26 MB** 的 `run_117650493.js`——这是本次审计能给出"源码级"结论的关键。
4. **静态审计**：对 26 MB 源码做定向检索（网络端点、遥测构造点、敏感字段邻近度、SDK 初始化开关）。
5. **实测交叉验证**：读取本机 `%USERPROFILE%\.cline\data\logs\code.log` 与 `global-settings.json`，核对"实际上报了什么"。

审计脚本与原始证据均保留在 `cline-audit/` 目录内。

## 三、Cline 的运行架构

```
┌──────────────────────────────────────────────────────────────┐
│  cline-app.exe  (Tauri 外壳, 16.9 MB)                        │
│   └─ WebView2 渲染进程                                        │
│        └─ Next.js 前端（390 个 chunk，brotli 内嵌在 exe 里）  │
│             ・无 i18n 框架，UI 文案全部硬编码                │
└───────────────┬──────────────────────────────────────────────┘
                │ HTTP / WebSocket（本地回环）
┌───────────────▼──────────────────────────────────────────────┐
│  code-sidecar.exe  (Bun 单文件, 143.9 MB)                    │
│   ・内含完整可读 JS 源码（26 MB）                            │
│   ・本地 Hub 服务（ws://127.0.0.1:25463/hub）                │
│   ・本地 SQLite：sessions / tasks / connectors / hub-events  │
└──────────────────────────────────────────────────────────────┘
```

要点：

- **前端无 i18n 框架**，所有界面文案硬编码在 bundle 里 —— 这正是必须走"运行时注入翻译层"的原因（见汉化包说明）。
- **后端源码可读**，因此"它到底发了什么"是可直接读代码确认的，不需要靠抓包推测。
- 所有与模型厂商的通信由 sidecar 发起，**使用你自己配置的 API Key**。

## 五、遥测到底发了什么（实测证据）

### 5.1 上报通道的判据：遥测适配层只看元数据

遥测事件统一经过 `OpenTelemetryAdapter.emitLog`，其构造逻辑为：

```js
emitLog(event, properties, required) {
  if (!this.logger) return;
  const attributes = this.flattenProperties(this.buildAttributes(properties, required));
  this.logger.emit({ severityText: "INFO", body: event, attributes });
}

buildAttributes(properties, required = false) {
  return {
    ...this.commonProperties,      // 仅通用属性
    ...this.metadata,              // 仅版本/平台
    ...properties,                 // 各事件自带的元数据
    ...this.distinctId ? { distinct_id: this.distinctId } : {}
  };
}
```

而 `metadata` 的构造是固定六项：

```js
createClineTelemetryServiceMetadata() {
  return {
    extension_version: "unknown", cline_type: "unknown", platform: "terminal",
    platform_version: process?.version || "unknown",
    os_type: process?.platform || "unknown",
    os_version: process?.platform === "win32" ? process?.env?.OS ?? "unknown" : "unknown"
  };
}
```

### 5.2 敏感参数被"长度化"处理

这是最有力的反证——开发者在事件构造处**刻意只传长度、不传内容**：

```js
// @mention 引用：只传类型与内容长度，不传内容
function captureMentionUsed(telemetry2, mentionType, contentLength) {
  emit(telemetry2, CORE_TELEMETRY_EVENTS.TASK.MENTION_USED,
       { mentionType, contentLength, timestamp: new Date().toISOString() });
}

// 搜索：只传 queryLength（查询长度），不是 query 本身
function captureMentionSearchResults(telemetry2, query, resultCount, searchType, isEmpty) {
  emit(telemetry2, CORE_TELEMETRY_EVENTS.TASK.MENTION_SEARCH_RESULTS, {
    queryLength: query.length, ...
  });
}

// 报错文本统一截断到 500 字符
const MAX_ERROR_MESSAGE_LENGTH = 500;
function truncateErrorMessage(errorMessage) {
  if (!errorMessage) return;
  return errorMessage.substring(0, MAX_ERROR_MESSAGE_LENGTH);
}
```

### 5.3 实测：本机日志里真实记录的上报内容

`%USERPROFILE%\.cline\data\logs\code.log` 中 `telemetry.*` 记录的完整属性集（原文摘录）：

```json
{"telemetrySink":"TelemetryLoggerSink","severity":"warn","event":"telemetry.provider_created",
 "properties":{"extension_version":"0.0.32","cline_type":"desktop","platform":"Cline Desktop",
 "platform_version":"0.0.32","os_type":"win32","os_version":"Windows 11 Pro",
 "provider":"opentelemetry","enabled":true,"logsExporter":"otlp","metricsExporter":"otlp",
 "tracesExporter":"","otlpProtocol":"http/json","hasOtlpEndpoint":true,
 "distinct_id":"cl-****（本机设备标识，已脱敏）","device_id":"cl-****（本机设备标识，已脱敏）"},
 "msg":"telemetry.required_event"}
```

```json
{"telemetrySink":"TelemetryLoggerSink","event":"user.extension_activated",
 "properties":{"extension_version":"0.0.32","cline_type":"desktop","platform":"Cline Desktop",
 "platform_version":"0.0.32","os_type":"win32","os_version":"Windows 11 Pro",
 "distinct_id":"cl-****（本机设备标识，已脱敏）","device_id":"cl-****（本机设备标识，已脱敏）"},
 "msg":"telemetry.event"}
```

**注意对比**：同一份日志里，含项目路径的那一行长这样——

```json

```

它**没有** `telemetrySink`、没有 `event`、没有 `properties` 字段。也就是说：**带路径的日志是本机普通日志，走的是另一条管道，不进遥测。**

### 5.4 关键量化验证

| 检查项 | 结果 |
|---|---|
| `workspaceRoot` 出现在任意 `capture(` / `emit(` / `recordCounter(` 调用 **600 字符邻域**内的次数 | **0 次** |
| 遥测脚本中 `filePath` / `file_path` / `prompt` / `userMessage` / `fileContent` / `contentPreview` 作为属性键 | **0 次** |
| `code.file.path` / `code.stacktrace` 出现位置 | 仅在 OpenTelemetry SDK 的**常量定义表**中（`exports.ATTR_CODE_FILE_PATH = "code.file.path"`），无任何赋值调用点 |
| `gen_ai.input.messages` / `gen_ai.output.messages` / `langfuse.observation.input` | 同上——仅常量定义，出现在 SDK 属性名清单里 |
| `Sentry.init` | 0 次 |

> 这一点很关键：**字符串出现 ≠ 数据被发送**。OTel SDK 会把自己支持的全部语义约定属性名定义成常量，因此 bundle 里必然出现 `gen_ai.input.messages` 这类名字。判定"是否真的发送"必须看**赋值调用点**，而不是关键词命中数。

## 六、代码 / 提示词是否外流：3 个"默认关闭但存在"的开关

这是本次审计**唯一需要用户主动注意**的部分。

### 开关 A — `CLINE_TRACE_RECORD_CONTENT`（Langfuse 内容录制）

```js
async function resolveAiSdkTelemetry(providerId, samplingKey) {
  if (!isClineProviderId(providerId)) return TELEMETRY_DISABLED;   // 仅 cline / cline-pass
  ...
  if (await isTelemetryOptedOutGlobally()) return TELEMETRY_DISABLED;
  const recordContent = isEnvTruthy(process.env.CLINE_TRACE_RECORD_CONTENT);
  return {
    isEnabled: true,
    integrations: integration,
    recordInputs:  recordContent,   // ← 默认 false
    recordOutputs: recordContent    // ← 默认 false
  };
}
```

- 触发条件：使用 **Cline 官方模型网关**（`cline` / `cline-pass`）× 设置环境变量 `CLINE_TRACE_RECORD_CONTENT=1`。
- 一旦开启：**提示词与模型回复会被录制**并送往 Langfuse 追踪后端。
- 默认：关闭。

### 开关 B — PostHog `enableFullAiCapture`（AI 事件全量捕获）

```js
function a15(key, opts) {
  return new PostHog(key, { host: "https://data.cline.bot", ...opts });
}
// 桌面端实际调用（无任何内容类选项）：
const apiKey = "***<内置项目密钥>";
const provider = apiKey && process.env.IS_TEST !== "true" && process.env.E2E_TEST !== "true"
  ? new o18({ client: a15(apiKey), config: {...} })
  : new NoOpFeatureFlagsProvider;
```

```js
this.captureMode = resolveCaptureMode();                       // 默认 "v0"
this.enableFullAiCapture = normalizedOptions.enableFullAiCapture === true;  // 默认 false
this._aiCaptureRouteActive = false;                            // 只有出现 $ai_* 事件才置 true
```

- 桌面端实例化时**没有传入任何内容相关选项**，`enableFullAiCapture` 保持 `false`。
- Cline 自身**从不调用** `captureAi`，也**从不调用** `captureException`（`$ai_` 前缀仅作为 SDK 常量存在）。
- 结论：PostHog 在本产品中只承担**特性开关**职责，不上报 AI 内容。

### 开关 C — PostHog 异常自动捕获 + 源码上下文

PostHog SDK 内含 error-tracking 模块，且具备读取本地源码给栈帧补 `context_line` / `pre_context` / `post_context` 的能力：

```js
async function addSourceContext(frames, openSourceFile, logger) {
  ... // 读取 frame.filename 对应文件的源码行，塞进 frame.context_line 等字段
}

this._exceptionAutocaptureEnabled = options.enableExceptionAutocapture || false;  // ← 默认 false
```

- 默认 `false`，且 Cline 未开启、未调用 `captureException` —— **处于休眠状态**。
- 该 SDK 同时内置了隐私缓解：`createRelativePathModifier(basePath = process.cwd())` 会把**绝对路径改写为相对路径**再上报。
- 残余风险：**若将来官方开启该项**，报错时栈帧附带的源码上下文会外流。

### 其他残余风险（低）

- `sdk.error` 遥测事件携带 `stack` 字段。实测样本中的栈只含打包内路径（`http://tauri.localhost/...`、`B:/~BUN/root/...`），**未出现用户项目绝对路径**；`error_message` 另有 500 字符截断。理论上若某第三方库把绝对路径写进栈，存在外泄可能。

## 八、如何关闭遥测

### 方式一：官方开关（推荐，最干净）

关闭 Cline 的遥测设置项，程序会写入全局设置文件：

```
%USERPROFILE%\.cline\data\settings\global-settings.json
```

把 `telemetryOptOut` 改为 `true`：

```json
{
  "autoUpdateEnabled": true,
  "telemetryOptOut": true,
  "tools": { "web_search": { "enabled": true } }
}
```

代码层面的关闭是**彻底**的——所有遥测服务创建入口都会先检查这个开关：

```js
function createConfiguredTelemetryService(options) {
  if (isTelemetryOptedOutGlobally()) {          // 读 global-settings.json
    return { telemetry: new OptedOutTelemetryService(options) };   // 直接返回"空实现"
  }
  ...
}
async function resolveAiSdkTelemetry(providerId) {
  ...
  if (await isTelemetryOptedOutGlobally()) return TELEMETRY_DISABLED;
}
```

注意：`isTelemetryOptedOutGlobally()` 在**文件缺失或 JSON 解析失败**时返回 `true`（即判定为"已退出"），因此该开关的行为是保守的。

关闭动作本身会上报一条 `user.opt_out` 事件（记录"有人退出了遥测"这一事实），此后不再上报。

### 方式二：网络层封堵（想更彻底）

在 `C:\Windows\System32\drivers\etc\hosts` 追加：

```
0.0.0.0 otel.cline.bot
0.0.0.0 data.cline.bot
```

或用防火墙禁止 `cline-app.exe` / `code-sidecar.exe` 访问上述域名。
副作用：特性开关与灰度能力失效（不影响核心编码功能）；若你使用 Cline 官方模型网关，`api.cline.bot` **不要**封。

### 方式三：只关内容类开关（保持功能遥测）

确保**不要**设置以下环境变量：`CLINE_TRACE_RECORD_CONTENT`、`POSTHOG_CAPTURE_MODE`。

## 九、最坏情况风险分级

| 等级 | 场景 | 前提条件 |
|---|---|---|
| 🟢 低 | 元数据 + 设备指纹被官方长期留存 | 默认行为，无前提 |
| 🟢 低 | 报错文本（≤500 字符）可能含片段路径 | 若第三方库栈含绝对路径 |
| 🟡 中 | 提示词与模型回复被录制外发 | **需**使用官方网关 **且** 人为设置 `CLINE_TRACE_RECORD_CONTENT=1` |
| 🟡 中 | 报错时的源码上下文外流 | **需**官方在后续版本开启 `enableExceptionAutocapture` |
| 🔴 高 | 整个代码库被上传 | **未发现任何相关代码路径**；唯一的代码外流是你主动配置的模型厂商 API |

---

## 十、给用户的 4 条建议

1. **改一行配置即可**：把 `global-settings.json` 的 `telemetryOptOut` 设为 `true`。这是最小成本的隐私提升。
2. **别设那两个环境变量**：`CLINE_TRACE_RECORD_CONTENT` 和 `POSTHOG_CAPTURE_MODE`，它们是"内容外流"的唯一闸门。
3. **厂商选择即数据边界**：真正会离开机器的代码内容只走你配置的模型 API。用官方网关时，请求会经 `api.cline.bot` 中转；若你的代码敏感，优先直连自建/自控的端点。
4. **`~/.cline/data/logs/code.log` 会记录项目路径**。要分享日志排障时，先脱敏这一行。
